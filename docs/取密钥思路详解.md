# 微信 4.x 本地库「取密钥」思路详解

> 适用对象:微信 4.x(xwechat 新架构,实测 **4.1.7.59 / x64**)本地 `db_storage` 下
> SQLCipher 加密数据库的**密钥恢复**。
>
> 本文只讲「思路与原理」,不贴完整源码;关键字段/偏移会在相应处给出,方便读者在
> 其它机器或版本上照做或校准。
>
> **使用边界(重要)**:本方法只用于**你自己电脑、你自己登录的微信账号**的数据找回与
> 备份。不得用于他人设备、他人账号,或任何未授权的数据访问。聊天数据属隐私,恢复
> 出的结果请自行妥善保管,勿公开外传。

---

## 0. 一句话总结

微信把每个数据库的加密密钥放在**它自己进程的内存里**,不落盘 → 我们**进入它的
内存,按结构把密钥读出来**,再**用密钥真开一次库验证**。核心四步:

**进内存(Frida)→ 找结构(字节指纹)→ 读指针(结构偏移)→ 真验证(sqlcipher3)。**

---

## 1. 前提:为什么密钥只能从内存拿

微信 4.x 的本地聊天库是 **SQLCipher 整库加密**:

- 每个账号目录 `...\xwechat_files\wxid_<id>_<suffix>\db_storage\` 下约有 **20 个
  `.db`**,聊天内容按分片存在 `message_N.db` / `biz_message_N.db`,另有 `contact.db`
  (联系人)、`session.db`(会话)等。
- **每个库一把独立随机的 32 字节 AES-256 原始密钥**,不是全账号共用的主密钥。
- 这些密钥**不以明文落盘**;只有「正在登录运行」的微信进程内存里才有。

由此得出几个**决定工具形态**的推论:

1. **只有当前登录的账号**的密钥在内存里 → 没登录的账号、从没被打开过的库
   (如 `migrate/unspportmsg.db`)天然取不到密钥,只能如实报失败,不是 bug。
2. 取钥必须**动态进进程读内存** → 需要微信在登录运行。
3. 这版(4.1.7.59)库文件头**没有可读的明文文件盐**,不能靠「磁盘盐」把内存里的
   密钥和某个 `.db` 一一配对 → **密钥与库的归属只能靠真验证**(见第 5 节)。

---

## 2. 三步主干

| 步骤 | 动作 | 手段 |
|---|---|---|
| S1 | **进得去** | Frida 附加微信主进程,注入脚本读它自己的内存 |
| S2 | **找得着** | 按 `codec_ctx` 结构的固定字节指纹,在可读内存里全文扫描定位 |
| S3 | **读得出** | 按结构偏移,顺指针链读到 32 字节原始 AES 密钥 |
| S4 | **算数验证** | 用 sqlcipher3 拿候选钥匙真开库,PASS 才算 |

S1–S3 产出的是**候选密钥**;S4 才把它们**归属到具体库并确认有效**。

---

## 3. S1 进得去:定位主进程 + Frida 附加

微信是多进程的(常驻多个 `Weixin.exe`)。**持有库加密上下文的通常是"最早创建"的
那个主进程**,其它子进程读不到。做法:

1. 列出所有 `Weixin.exe` 的 PID;
2. 按**创建时间升序**排,从最早的逐个试;
3. 用 Frida `attach(pid)` 附加 → 注入一段脚本 → `script.load()` 在目标进程里执行;
4. 脚本扫完把结果 `send(...)` 发回 Python 端,收到即 `detach` 离开。

特点:**只读内存、不改文件、不杀进程**。附加失败(权限、进程已退、版本结构不同)就
如实报错,换下一个 PID 或收工,绝不硬来。

> 附带一步「账号自检」:用 psutil 读进程 `open_files()`,凡句柄路径含
> `<root>\wxid_xxx_suffix\db_storage\` 就是它正在服务的账号。若目标账号与当前
> 登录账号不一致,直接中止——避免「拿 A 账号的钥匙去验 B 账号的库」白跑一轮。

---

## 4. S2 找得着:按字节指纹定位 codec_ctx

微信给每个库做 SQLCipher 加密、打开该库时,内存里会有一个 **`codec_ctx`** 结构体,
记录该库的加解密上下文(盐、读写用的 cipher 上下文等)。

它在偏移 `+0x0c` 起有一串**相对固定的字节指纹**:

```
+0x0c 起 20 字节(五组小端 u32):
  0x10 0x00 0x00 0x00   0x20 0x00 0x00 0x00   0x10 0x00 0x00 0x00
  0x10 0x00 0x00 0x00   0x10 0x00 0x00 0x00
→ 十六进制串: 1000000020000000100000001000000000100000
```

扫描做法:

1. 枚举进程所有**可读内存区**(protection 含 `r--`/`r-x`/`rw-`/`rwx`),合并相邻区,
   滤掉 >1GB 的巨块和空块;
2. 每段用 `Memory.scanSync(base, size, needle)` 全文搜这段指纹;
3. 命中地址 **减 0x0c** = `codec_ctx` 结构头;按地址去重,一个结构只处理一次。

多个库各自有各自的 `codec_ctx`,但这段结构头不变,所以全文会命中「当前已加载的
所有库」的上下文。

---

## 5. S3 读得出:顺指针链取 32 字节原始密钥

对每个 `codec_ctx`(结构头读 0x80 字节),按已知偏移取:

| 偏移(相对 codec_ctx) | 内容 |
|---|---|
| `+0x48` | 盐:先按指针解引用读 16 字节;读不通则内联读 16 字节(尽力而为,读不到不阻断收钥) |
| `+0x68` | `read_ctx` —— 读方向 cipher 上下文指针 |
| `+0x70` | `write_ctx` —— 写方向 cipher 上下文指针(读写两份通常指向同一把钥匙,取并集去重) |

再顺每个 cipher 上下文(读它头 0x30 字节):

| 偏移(相对 cipher ctx) | 内容 |
|---|---|
| `+0x00` | `derive_key` 标志(u32,是否由口令派生) |
| `+0x04` | `pass_sz` 口令长度(u32) |
| `+0x08` | 指向 **32 字节原始 AES 密钥** 的指针 → 解引用读 32 字节 ← **核心产出** |
| `+0x10` | 指向 32 字节 hmac 摘要的指针(元信息) |

把读到的 32 字节转 hex,按**内容去重**,得到「这个进程内存里所有不同的密钥」全集。
任何一处指针解引用失败就跳过该条(防止指纹误命中时乱读);只有真正读通上下文、
拿到 32 字节的才收录。

---

## 6. S4 算数:真验证(唯一标准)

**取钥阶段扫出来的只是"候选",工具不信任自己扫出来的东西。** 下一步 `verify` 用
sqlcipher3 **离线真开一次库**:

```sql
PRAGMA key = "x'<hex密钥>'";
SELECT count(*) FROM sqlite_master;   -- 能读出表 = 这把钥匙真能开这个库(PASS)
```

- 密钥与库的**归属以这次 PASS 为准**,绝不"看着像就当成对";
- 4.1.7.59 库头无明文盐 → 盐→库映射为空,就用「内存密钥全集 × 每个库」逐个真验;
- 错钥会触发 sqlcipher3 底层 C 层往 stderr 刷 hmac 校验失败日志,批量试之前先
  静音 fd 2,避免刷屏/乱码;
- 只把**真 PASS** 的钥匙写入 verified 清单,导出聊天时以它为唯一来源。

## 7. 诚实失败边界(这些不是 bug)

| 情形 | 结果 |
|---|---|
| 目标账号没登录运行 | 内存无它的 codec_ctx → 账号自检拦下,或扫描无果 |
| 某库从未被打开(空闲库) | 内存无它的上下文 → 无候选 → verify 如实 FAIL、不写入 |
| 微信版本换了结构 | 指纹/偏移对不上 → 扫不到或验不过 → 如实报 FAIL,提示回传,不伪造 |
| 微信已退出 | 无法附加 → 明确提示先登录运行 |

---

## 8. 推广到其它机器 / 版本,需要重新校准什么

思路通用,**具体数值不通用**。换版本或架构时,先确认这几点:

1. **进程形态**:是否仍多进程、主进程最早启动、且它持有 codec?用 `find` 看 PID 与
   其服务的账号。
2. **指纹串**:`+0x0c` 那五组 u32 是否仍是 `10 20 10 10 10`?校准方法:先拿到一把
   **已知钥匙**(例如先在已跑通的机器上取得),再在内存里反查这 32 字节的引用地址,
   回推 codec_ctx 与各偏移,逐项修正。
3. **盐**:若新版本库头有可读明文盐,优先走「盐→库」精确映射(更快);没有则走
   真验证兜底。
4. **验证手段永远不变**:无论哪个版本,最终都以 sqlcipher3 `PRAGMA key` 真 PASS 为
   唯一判据 —— 这保证"结构猜错"只会导致 FAIL,绝不会产出假钥匙。

---

## 9. 一句话收束

> **进内存(Frida)→ 按指纹找 codec_ctx → 按偏移链读 32 字节原始密钥 →
> sqlcipher3 真开库定归属。结构数值按版本校准,验证标准永远不变。**
